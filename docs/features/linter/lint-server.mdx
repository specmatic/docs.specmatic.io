# Skeptic Lint Server <CommercialBadge/>

:::caution[Experimental]
Skeptic Lint Server currently supports OpenAPI specifications. The server is experimental, may change, and requires a Specmatic Enterprise service-account license.
:::

Skeptic Lint Server provides an HTTP API for linting one or more OpenAPI specifications in a batch. It loads a shared lint configuration from Git, applies a profile (a named set of lint rules and severities) to each specification, and returns one SARIF report per specification. SARIF is a standard format for security and code analysis results. The server then sends the batch to Specmatic Insights in the background.

This guide starts with server setup, then walks through the API endpoints and report delivery. The [OpenAPI contract](https://github.com/specmatic/enterprise/blob/main/linter/lint-server.yaml) lists every request and response field and error code.

## 1. Start the server

You need the Specmatic Enterprise Docker image and a valid service-account license. The license enables the server's licensed linting features and Insights publishing. Provide it through your deployment's secret manager as `SPECMATIC_LICENSE_CONTENT`, or mount the license file and set `SPECMATIC_LICENSE_PATH` to its location in the container.

The command below starts the server on port `8000`. Set `SPECMATIC_LICENSE_CONTENT` in your shell or deployment environment before running it.

```bash
docker run --rm \
  -p 8000:8000 \
  -e SPECMATIC_LICENSE_CONTENT="$SPECMATIC_LICENSE_CONTENT" \
  specmatic/enterprise \
  lint-server \
  --port=8000
```

The lint request supplies the configuration repository and the download URL for each OpenAPI file. By default, the configuration repository must contain `specmatic-linter.yaml` at its root.

## 2. Choose startup options

The server listens on port `8000` by default. The following options configure authentication, source restrictions, HTTPS, and publishing behavior. Add them after `lint-server` in the Docker command when needed.

| Option | Purpose | Default |
| --- | --- | --- |
| `--port` | HTTP port, or HTTPS port when TLS is enabled. | `8000` |
| `--jwt-issuer` and `--jwt-jwks-url` | Trusted token issuer and its public signing key endpoint. Repeat the pair for each issuer. | Caller authentication off |
| `--jwt-audience` | Audience required in caller tokens. | None |
| `--jwt-match` | Additional claim/value required in caller tokens. Repeat as needed. | None |
| `--allowed-config-repo-url` | Configuration Git repository the server may load. Repeat to allow multiple repositories. | Any HTTP(S) repository |
| `--allowed-spec-download-host` | Hostname allowed for specification downloads. Repeat to allow multiple hosts. | Any host |
| `--tls-keystore` and `--tls-key-alias` | PKCS#12 keystore and private-key alias; enables HTTPS. | TLS off |
| `--max-spec-size-code-points` | Maximum decoded characters per specification. | `5242880` |
| `--background-job-max-retries` | Number of retries after the first failed Insights attempt. | `3` |
| `--background-job-retry-initial-delay-seconds` | Seconds before the first retry. | `3` |
| `--background-job-retry-multiplier` | Factor used to increase retry delays. | `3` |
| `--debug` | Include lint-server diagnostic and routine probe events in logs. | Off |

### Caller authentication

Caller authentication is optional. To enable it, configure `--jwt-issuer`, `--jwt-jwks-url`, and `--jwt-audience`. Clients then send a signed JSON Web Token (JWT) in the `Authorization: Bearer <JWT>` header. Tokens must use RS256, match the configured issuer and audience, and include an expiration claim (`exp`). The server retrieves signing keys only from the configured JWKS endpoints.

Use `--jwt-match` to require specific token claims. For string values, the configured text must appear as a case-sensitive substring. For arrays, every configured value must appear as an exact element. Health, readiness, status, and API documentation endpoints do not require a caller token; keep operational endpoints on an internal network. The service-account license is separate from caller authentication, and caller tokens are not sent to Insights or source repositories.

### Source allowlists

Use `--allowed-config-repo-url` to restrict configuration repository URLs and `--allowed-spec-download-host` to restrict specification download hosts. Configuration URLs must exactly match an allowed URL after embedded credentials are removed. Specification URLs must use an allowed hostname. If no values are configured, those sources are unrestricted. A blocked source returns `403` and is not fetched. Redirect destinations are outside these allowlist checks.

Configuration repository URLs must use HTTP or HTTPS. If a private source requires credentials, provide them securely with that source URL. Credentials embedded in source URLs are removed from logs, responses, reports, and Insights data.

### HTTPS

To serve HTTPS directly, mount a PKCS#12 keystore containing the server certificate and private key, then configure `--tls-keystore` and `--tls-key-alias` together. Supply `SPECMATIC_TLS_KEYSTORE_PASSWORD` and, if different, `SPECMATIC_TLS_PRIVATE_KEY_PASSWORD` through your secret manager. With TLS enabled, the server serves HTTPS only on the selected port. Without TLS, use HTTP for local development or run behind an HTTPS-enabled ingress or proxy.

The default `--max-spec-size-code-points` limit is 5,242,880 decoded Unicode code points per specification (about 5 MiB for ASCII text). It measures decoded characters, not request size or bytes. Increase it only after checking memory use and parser capacity.

## 3. Explore the API

After the server starts, open [http://localhost:8000/api-docs/](http://localhost:8000/api-docs/) for interactive API documentation. To download the OpenAPI contract directly, use [http://localhost:8000/api-docs/openapi.yaml](http://localhost:8000/api-docs/openapi.yaml).

## 4. Check health and readiness

Use these endpoints to check whether the server is alive and ready for lint requests. They can also be configured as container or Kubernetes probes.

```bash
curl -i http://localhost:8000/health
curl -i http://localhost:8000/readiness
```

- `GET /health` checks that the server is running and its service-account license is valid. It returns `503` with `LICENSE_EXPIRED` after the license expires.
- `GET /readiness` tells you whether the server accepts new lint requests. It can return `503` when the license is nearing expiry, Insights delivery is blocked, or the server is shutting down. Check `/status` for the reason.

## 5. Submit a lint request

Send a `POST` request to `/skeptic/lint/reports`. Save this example as `lint-request.json` and replace the sample URLs and IDs with your own:

```json
{
  "config": {
    "git": {
      "url": "https://github.com/specmatic/central-lint-config.git",
      "branch": "main"
    }
  },
  "repository": {
    "id": "orders-api",
    "name": "Orders API",
    "url": "https://git.example.com/platform/orders-api",
    "branch": "main",
    "specifications": [
      {
        "id": "orders-v1",
        "path": "contracts/orders/openapi.yaml",
        "downloadUrl": "https://specs.example.com/orders/openapi.yaml",
        "profile": "default"
      }
    ]
  },
  "ci": {
    "buildId": "234",
    "runAttempt": "1",
    "metadata": { "pipelineName": "orders-api-ci" }
  }
}
```

The main request fields are:

- `config.git.url` identifies the Git repository containing the lint configuration. `branch` is optional; if omitted, the repository's default branch is used.
- `repository.id`, `repository.url`, and `repository.branch` describe the Git repository that owns the specifications. They are metadata for Insights; the server does not fetch specification files from this repository. `repository.name` is optional.
- Each specification needs a unique `id` and a repository-relative `path`. The server downloads it from `downloadUrl`, which must be an absolute HTTP(S) URL. The `profile` is optional; if omitted, the server uses the `default` profile.
- `ci` is optional. If included, it must contain `buildId`. `runAttempt` and flat string `metadata` values are optional.

The configuration and specification URLs must be reachable from the server. If a private source needs credentials, provide them through your secret manager in the source URL; the server removes URL credentials from logs, responses, reports, and Insights data. The server checks that every requested profile exists before downloading the specifications. It then lints the whole batch. If any specification cannot be downloaded or linted, the request fails without partial reports or an Insights submission. All reports in the batch use the same configuration version.

If caller authentication is enabled, set `LINT_SERVER_JWT` to a valid token from your identity provider and include it as a bearer token. The optional `X-Request-Id` header must contain a UUID. Reuse the same ID when retrying the same request so Insights can recognize duplicate deliveries.

```bash
curl -i http://localhost:8000/skeptic/lint/reports \
  -H "Authorization: Bearer ${LINT_SERVER_JWT}" \
  -H "X-Request-Id: 6ab54da1-f1e1-4c5e-94cc-742467531dce" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  --data-binary @lint-request.json
```

If caller authentication is disabled, remove the `Authorization` header. The server returns the request ID in a response header and, for errors, in the response body. It records the ID in logs and sends it to Insights as an idempotency key.

## 6. Read the response

HTTP `200` means every specification was linted and the batch was accepted for background delivery to Insights. It does not mean lint passed or that Insights has finished processing the reports. The response contains an overall result, the configuration version, the linter version, and one report per specification.

A report has `result: "failure"` if it contains a non-ignored error-level finding. Warnings alone produce `success`. The `maturity` value is a separate assessment of rule compliance; it can be `non-conformant`, `baseline`, `silver`, `gold`, `platinum`, or `null`.

Use the stable error `code` and request ID to diagnose failures. Common responses include:

- `UNKNOWN_PROFILE` (`400`): a requested profile is not defined in the configuration.
- `LICENSE_DENIED` (`402`): the license does not allow new lint work.
- `CONFIG_INVALID` (`422`): the configuration repository, branch, or configuration file is missing or invalid.
- `SPEC_TOO_LARGE` (`422`): a downloaded specification exceeds the configured size limit.
- `CONFIG_UNAVAILABLE` (`503`): the server could not load configuration because the source or credentials are unavailable.
- `SERVER_NOT_READY` or `SERVICE_UNAVAILABLE` (`503`): the server cannot accept new work; check its readiness and operational status.

See the [OpenAPI contract](https://github.com/specmatic/enterprise/blob/main/linter/lint-server.yaml) for the full error mapping.

If you repeat a `POST`, the server runs linting again; it does not replay an earlier response. For the same evaluation, keep the request ID and input unchanged. Insights can use that ID to avoid processing a duplicate delivery. Use a new ID when the specification, configuration, profile, or metadata changes.

## 7. Check report delivery

The lint response does not wait for Insights. The server sends each completed batch in the order received. Temporary failures are retried. If the oldest batch exhausts its configured retries, later batches wait and readiness becomes unhealthy until delivery recovers. A permanent Insights rejection is recorded and does not block later batches.

The delivery queue is held in memory. A restart or forced termination can lose reports that have not been delivered. During a controlled shutdown, the server makes a best-effort attempt to send queued reports before it exits.

Use `GET /status` to inspect the current server instance, including when readiness is failing:

```bash
curl -i http://localhost:8000/status
```

The response shows the instance start time, license and readiness states, Insights delivery counts and batches, and cached configuration versions. It excludes credentials, tokens, report contents, and temporary file paths. State resets when the process restarts. In a multi-instance deployment, each response describes only the instance that handled the request. Keep `/status` on an internal operations network. See the [OpenAPI contract](https://github.com/specmatic/enterprise/blob/main/linter/lint-server.yaml) for the response fields.
