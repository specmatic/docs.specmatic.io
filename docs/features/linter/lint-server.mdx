# Skeptic Lint Server <CommercialBadge/>

:::caution[Experimental]
Skeptic Lint Server currently supports OpenAPI specifications. The server is experimental, may change, and requires a Specmatic Enterprise service-account license.
:::

Skeptic Lint Server provides an HTTP API for linting one or more OpenAPI specifications in a batch. It loads a shared lint configuration from Git, applies a profile (a named set of lint rules and severities) to each specification, and returns one SARIF report per specification. SARIF is a standard format for security and code analysis results. The server then sends the batch to Specmatic Insights in the background.

Follow the steps below to start the server, explore its API, submit a batch, and check whether its reports reached Insights. The [OpenAPI contract](https://github.com/specmatic/enterprise/blob/main/linter/lint-server.yaml) lists all request and response fields and error codes.

## 1. Start the server

You need the Specmatic Enterprise Docker image and a valid service-account license. The license enables the server's licensed linting features and Insights publishing. Provide it through your deployment's secret manager as `SPECMATIC_LICENSE_CONTENT`, or mount the license file and set `SPECMATIC_LICENSE_PATH` to its location in the container.

The command below starts the server on port `8000`. Make sure `SPECMATIC_LICENSE_CONTENT` is set in your shell or deployment environment before running it.

```bash
docker run --rm \
  -p 8000:8000 \
  -e SPECMATIC_LICENSE_CONTENT="$SPECMATIC_LICENSE_CONTENT" \
  specmatic/enterprise \
  lint-server \
  --port=8000
```

The server needs two sources when you submit a request: a Git repository containing a `specmatic-linter.yaml` configuration file, and a URL from which it can download each OpenAPI specification. The request example below shows how to provide them.

## 2. Explore the API

After the server starts, open [http://localhost:8000/api-docs/](http://localhost:8000/api-docs/) for interactive API documentation. To download the OpenAPI contract directly, use [http://localhost:8000/api-docs/openapi.yaml](http://localhost:8000/api-docs/openapi.yaml).

## 3. Check server health and readiness

Use these endpoints to check whether the server is alive and ready for lint requests. They can also be configured as container or Kubernetes probes.

```bash
curl -i http://localhost:8000/health
curl -i http://localhost:8000/readiness
```

- `GET /health` checks that the server is running and its service-account license is valid. It returns `503` with `LICENSE_EXPIRED` after the license expires.
- `GET /readiness` tells you whether the server accepts new lint requests. It can return `503` when the license is nearing expiry, Insights delivery is blocked, or the server is shutting down. This gives the server time to finish queued reports or stop safely. Check `/status` for the reason.

## 4. Submit a lint request

Send a `POST` request to `/skeptic/lint/reports`. Save this example as `lint-request.json` and replace the sample URLs and IDs with your own:

```json
{
  "config": {
    "git": {
      "url": "https://github.com/specmatic/central-lint-config.git",
      "branch": "main"
    }
  },
  "repository": {
    "id": "orders-api",
    "name": "Orders API",
    "url": "https://git.example.com/platform/orders-api",
    "branch": "main",
    "specifications": [
      {
        "id": "orders-v1",
        "path": "contracts/orders/openapi.yaml",
        "downloadUrl": "https://specs.example.com/orders/openapi.yaml",
        "profile": "default"
      }
    ]
  },
  "ci": {
    "buildId": "234",
    "runAttempt": "1",
    "metadata": { "pipelineName": "orders-api-ci" }
  }
}
```

The request fields have different roles:

- `config.git.url` points to the Git repository containing the lint configuration. It must use HTTP or HTTPS. The `branch` is optional; if omitted, the repository's default branch is used. By default, the server looks for `specmatic-linter.yaml` at the repository root.
- `repository.id`, `repository.url`, and `repository.branch` describe the Git repository that owns the specifications. They are required metadata for Insights; the server does not fetch specification files from this repository. `repository.name` is optional.
- Each entry in `repository.specifications` needs a unique `id` and a repository-relative `path`. The server downloads the file from `downloadUrl`, which must be provided as an absolute HTTP(S) URL for every specification. The `path` is returned in the report and sent to Insights. `profile` is optional; when omitted, the server uses the `default` profile.
- `ci` is optional. If included, it must contain `buildId`. `runAttempt` and flat string `metadata` values are optional.

Configuration and specification URLs must be reachable from the server. If a private source requires credentials, provide them securely with that source URL. Credentials embedded in source URLs are removed from logs, responses, reports, and Insights data.

If caller authentication is enabled, set `LINT_SERVER_JWT` to a valid token from your identity provider and include it as a bearer token. The optional `X-Request-Id` header must contain a UUID. Reuse the same ID when retrying the same request so Insights can recognize duplicate deliveries.

```bash
curl -i http://localhost:8000/skeptic/lint/reports \
  -H "Authorization: Bearer ${LINT_SERVER_JWT}" \
  -H "X-Request-Id: 6ab54da1-f1e1-4c5e-94cc-742467531dce" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  --data-binary @lint-request.json
```

Remove the `Authorization` header if caller authentication is disabled. The server returns the request ID in a response header and, for errors, in the response body. It also records the ID in logs and sends it to Insights as an idempotency key.

The server validates the request and checks that all requested profiles exist before downloading specifications. It then lints the whole batch. If any specification cannot be downloaded or linted, the request fails without partial reports or an Insights submission. All reports in a batch use the same configuration version.

## 5. Understand the response

HTTP `200` means every specification was linted and the batch was accepted for background delivery to Insights. It does not mean lint passed or that Insights has finished processing the reports. The response contains an overall result, the configuration version, the linter version, and one report per specification.

A report has `result: "failure"` if it contains a non-ignored error-level finding. Warnings alone produce `success`. The `maturity` value is a separate assessment of rule compliance; it can be `non-conformant`, `baseline`, `silver`, `gold`, `platinum`, or `null`.

Use the stable error `code` and request ID to diagnose failures. Common responses include:

- `UNKNOWN_PROFILE` (`400`): a requested profile is not defined in the configuration.
- `LICENSE_DENIED` (`402`): the license does not allow new lint work.
- `CONFIG_INVALID` (`422`): the configuration repository, branch, or configuration file is missing or invalid.
- `SPEC_TOO_LARGE` (`422`): a downloaded specification exceeds the configured size limit.
- `CONFIG_UNAVAILABLE` (`503`): the server could not load configuration because the source or credentials are unavailable.
- `SERVER_NOT_READY` or `SERVICE_UNAVAILABLE` (`503`): the server cannot accept new work; check its readiness and operational status.

The full error mapping is in the [OpenAPI contract](https://github.com/specmatic/enterprise/blob/main/linter/lint-server.yaml).

If you repeat a `POST`, the server runs linting again; it does not replay an earlier response. For the same evaluation, keep the request ID and input unchanged. Insights can use that ID to avoid processing a duplicate delivery. Use a new ID when the specification, configuration, profile, or metadata changes.

## 6. Check report delivery

The lint response does not wait for Insights. The server sends each completed batch in the background, in the order received. Temporary failures are retried. If the oldest batch exhausts its configured retries, later batches wait and readiness becomes unhealthy until delivery recovers. A permanent Insights rejection is recorded and does not block later batches.

The delivery queue is held in memory. A restart or forced termination can lose reports that have not been delivered. During a controlled shutdown, the server makes a best-effort attempt to send queued reports before it exits.

Use `GET /status` to inspect this server instance, including when readiness is failing:

```bash
curl -i http://localhost:8000/status
```

The response shows the instance start time, license and readiness states, Insights delivery counts and batches, and cached configuration versions. State resets when the process restarts. In a multi-instance deployment, each response describes only the instance that handled the request. Keep `/status` on an internal operations network. The [OpenAPI contract](https://github.com/specmatic/enterprise/blob/main/linter/lint-server.yaml) defines the response fields.

## Deployment options

For a shared or production deployment, you can configure caller authentication, source allowlists, HTTPS, and the maximum specification size. These settings are optional. The options below are arguments to the `lint-server` command; the [OpenAPI contract](https://github.com/specmatic/enterprise/blob/main/linter/lint-server.yaml) documents the HTTP request and response.

### Caller authentication

Caller authentication is optional. To enable it, pass `--jwt-issuer` and `--jwt-jwks-url` for each trusted issuer, and set `--jwt-audience` to the service the token is intended for. Clients then provide a signed JSON Web Token (JWT). Tokens must use RS256, have a valid signature, match the configured issuer and audience, and include an expiration (`exp`). Use `--jwt-match` to require additional token claims.

Clients send the token in the `Authorization: Bearer <JWT>` header. Health, readiness, status, and API documentation endpoints do not require caller authentication, so keep operational endpoints on an internal network. The server's service-account license is separate from caller authentication; caller tokens are not sent to Insights or source repositories.

### Source allowlists

Use `--allowed-config-repo-url` to restrict configuration Git URLs and `--allowed-spec-download-host` to restrict specification download hosts. Config URLs must exactly match an allowed URL after embedded credentials are removed; specification URLs must use an allowed hostname. If no values are configured, those sources are unrestricted. A blocked source returns `403` and is not fetched. Allowlists check the URLs in the request; redirect destinations are outside these checks.

### HTTPS

To serve HTTPS directly, mount a PKCS#12 keystore containing the server certificate and private key, then configure `--tls-keystore` and `--tls-key-alias` together. Supply `SPECMATIC_TLS_KEYSTORE_PASSWORD` and, if different, `SPECMATIC_TLS_PRIVATE_KEY_PASSWORD` through your secret manager. With TLS enabled, the server serves HTTPS only on the selected port. Without TLS, use HTTP for local development or run behind an HTTPS-enabled ingress or proxy.

### Specification size

The default `--max-spec-size-code-points` limit is 5,242,880 decoded Unicode code points per specification (about 5 MiB for ASCII text). This measures decoded characters, not request size or bytes. Increase the limit only after checking memory use and parser capacity.
