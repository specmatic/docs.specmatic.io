# Skeptic Lint Server <CommercialBadge/>

:::caution[Experimental]
Skeptic Lint Server currently supports OpenAPI specifications. The server is experimental and requires a Specmatic Enterprise service-account license.
:::

Skeptic Lint Server lints one or more OpenAPI specifications against a shared Git configuration and returns a SARIF report for each. It publishes completed report batches to Specmatic Insights in the background.

## 1. Start the server

Provide a service-account license through your deployment secret manager as `SPECMATIC_LICENSE_CONTENT`, or mount a license file and set `SPECMATIC_LICENSE_PATH`.

```bash
docker run --rm \
  -p 8000:8000 \
  -e SPECMATIC_LICENSE_CONTENT="$SPECMATIC_LICENSE_CONTENT" \
  specmatic/enterprise \
  lint-server
```

The server listens on port `8000`. A lint request supplies the configuration repository and each specification's download URL. By default, the config repository contains `specmatic-linter.yaml` at its root.

## 2. Configure startup options

All options are optional. Add them after `lint-server` in the command above.

| Option | Purpose | Default |
| --- | --- | --- |
| `--port` | HTTP or HTTPS listener port. | `8000` |
| `--jwt-issuer`, `--jwt-jwks-url` | Trusted caller token issuer and signing keys. Repeat the pair per issuer. | Caller authentication off |
| `--jwt-audience` | Required token audience. | None |
| `--jwt-match` | Additional claim/value requirement. Repeat as needed. | None |
| `--allowed-config-repo-url` | Allowed configuration repository. Repeat as needed. | Any HTTP(S) URL |
| `--allowed-spec-download-host` | Allowed specification download host. Repeat as needed. | Any host |
| `--tls-keystore`, `--tls-key-alias` | PKCS#12 keystore and key alias; enables HTTPS. | TLS off |
| `--max-spec-size-code-points` | Maximum decoded code points per specification. | `5242880` |
| `--background-job-max-retries` | Insights retries after the initial attempt. | `3` |
| `--background-job-retry-initial-delay-seconds` | Delay before the first retry. | `3` |
| `--background-job-retry-multiplier` | Retry delay multiplier. | `3` |
| `--debug` | Add diagnostic and probe events to logs. | Off |

<details>
<summary>Authentication, source access, and HTTPS</summary>

Caller authentication uses RS256 JWTs with a required `exp` claim. Configure issuer, JWKS URL, and audience, then send `Authorization: Bearer <JWT>`. Use `--jwt-match` for additional claims; strings match case-sensitive substrings, while arrays require each configured value as an exact element.

Configuration allowlists match the exact URL after embedded credentials are removed; specification allowlists match the hostname. Empty allowlists allow any source. Configuration URLs use HTTP(S). Credentials for private configuration and specification sources are separate; keep them in your secret manager. Credentials are redacted from logs, reports, and Insights data.

For HTTPS, mount a read-only PKCS#12 keystore with the certificate chain and private key, and set `--tls-keystore`, `--tls-key-alias`, and `SPECMATIC_TLS_KEYSTORE_PASSWORD`. If the key has a separate password, set `SPECMATIC_TLS_PRIVATE_KEY_PASSWORD` too. HTTPS serves on the selected port.

The specification size limit applies to decoded Unicode code points per file, not request size or bytes. Increase it only after checking memory use and parser capacity.

</details>

## 3. Explore the API

After the server starts, open [interactive API documentation](http://localhost:8000/api-docs/) or download the [OpenAPI schema](http://localhost:8000/api-docs/openapi.yaml). For a remote server, replace `localhost:8000` with its address. These endpoints are unauthenticated and remain available when lint requests are not ready.

## 4. Check health and readiness

```bash
curl -i http://localhost:8000/health
curl -i http://localhost:8000/readiness
```

| Endpoint | Use | Key behavior |
| --- | --- | --- |
| `GET /health` | Liveness probe. | Returns `200` through the license expiry time, including the final ten-minute drain; afterward returns `503 LICENSE_EXPIRED`. |
| `GET /readiness` | Route new lint work. | Returns `200` when ready; `503` lists active reason codes. |

Readiness can be affected by license expiry, blocked Insights delivery, or graceful shutdown. The ten-minute license drain pauses new lint work with `402 LICENSE_DENIED` so queued reports can be processed. A ready response does not guarantee that a particular request's config, profile, source, or queue capacity is valid.

## 5. Submit a lint request

Send `POST /skeptic/lint/reports`. This example includes optional CI metadata; remove the `ci` object if it is not needed.

```json
{
  "config": {
    "git": {
      "url": "https://github.com/specmatic/central-lint-config.git",
      "branch": "main"
    }
  },
  "repository": {
    "id": "orders-api",
    "name": "Orders API",
    "url": "https://git.example.com/platform/orders-api",
    "branch": "main",
    "specifications": [
      {
        "id": "orders-v1",
        "path": "contracts/orders/openapi.yaml",
        "downloadUrl": "https://specs.example.com/orders/openapi.yaml",
        "profile": "default"
      }
    ]
  },
  "ci": {
    "buildId": "234",
    "metadata": { "pipelineName": "orders-api-ci" }
  }
}
```

The request requires a configuration URL, repository ID/URL/branch, and at least one specification. Each specification needs a unique ID, repository-relative path, and download URL. The config branch and profile are optional; the server uses the repository default branch and `default` profile when omitted. The config URL must use HTTP(S); specification downloads accept HTTP(S) URLs and JSON or YAML content. `repository.url` and `repository.branch` are Insights metadata; the server fetches files from `downloadUrl`. If `ci` is included, `buildId` is required; `runAttempt` defaults to `"1"`, and metadata values must be strings.

The server authenticates the caller when enabled, validates the request and allowlists, loads configuration and resolves profiles, then downloads and lints the full batch against one config snapshot. A successful request returns all reports and queues the batch for Insights; a failed specification does not produce a partial response.

```bash
curl -i http://localhost:8000/skeptic/lint/reports \
  -H "Authorization: Bearer ${LINT_SERVER_JWT}" \
  -H "X-Request-Id: 6ab54da1-f1e1-4c5e-94cc-742467531dce" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json" \
  --data-binary @lint-request.json
```

When caller authentication is off, omit the `Authorization` header. `X-Request-Id` is optional; the server generates one when absent. Reuse the same ID and input for a retry of the same evaluation, and use a new ID when the evaluation changes. The ID is used as Insights' `Idempotency-Key`; the API runs linting for each `POST` and does not replay an earlier response.

## 6. Read the response

HTTP `200` means all reports were generated and accepted into the background Insights queue. It does not indicate whether lint passed or whether Insights finished processing. Each report contains a SARIF 2.1.0 document; batch and per-spec results are `success` or `failure`. Warnings alone do not cause failure. The response also identifies the configuration snapshot and linter version used.

Handle errors by stable `code` and HTTP status; use `requestId` to correlate logs. Common errors:

| Status | Common codes | Next step |
| --- | --- | --- |
| `400` | `INVALID_REQUEST`, `UNKNOWN_PROFILE` | Correct request fields or profile. |
| `401` / `403` | `INVALID_TOKEN`, `ACCESS_DENIED`, `*_URL_NOT_ALLOWED` | Check caller token, claim rules, and source allowlists. |
| `402` | `LICENSE_DENIED` | Check the service-account license. |
| `422` | `CONFIG_INVALID`, `INVALID_SPECIFICATION`, `SPEC_TOO_LARGE` | Correct the config or specification. |
| `500` | `INTERNAL_ERROR` | Contact the operator with the request ID. |
| `502` / `504` | `SPEC_FETCH_FAILED`, `AUTHENTICATION_UNAVAILABLE`, `SPEC_FETCH_TIMEOUT` | Check source or JWKS availability. |
| `503` | `CONFIG_UNAVAILABLE`, `SERVER_NOT_READY`, `SERVICE_UNAVAILABLE` | Check `/readiness` and `/status`; retry after recovery. |

For all fields, status codes, headers, and error variants, use the running server's `/api-docs/` or `/api-docs/openapi.yaml` endpoint. A `503` may include `Retry-After`. There is no report retrieval endpoint.

## 7. Configuration updates

The server caches configuration by repository and branch and refreshes it every five minutes. If a refresh fails, the last snapshot is marked stale; the next lint request must load the configuration successfully before it can proceed. A configuration refresh issue alone does not make the server unready.

## 8. Insights publishing

The server publishes one ordered SARIF batch per completed lint request using its service-account license. Delivery is asynchronous and FIFO. An Insights success confirms acceptance for processing.

| Insights request detail | Value |
| --- | --- |
| Authentication | `Authorization: license <license UUID>` |
| Idempotency | Request ID sent as `Idempotency-Key`; Insights acknowledges an accepted duplicate without creating another build. |
| Encoding | JSON compressed with gzip. |
| Reports | One SARIF 2.1.0 report per specification, in request order. |
| CI and repository context | Build ID, run attempt, repository ID/name/URL/branch, when provided. |
| Metadata | Caller `ci.metadata` plus server fields: `requestId`, `configCommitSha`, `configRepoUrl`, `linterVersion`, and `specifications`. Server values take precedence. |

`specifications` is a compact JSON string containing each specification's ID, path, and resolved profile. The queue is in memory, so reports that have not been delivered can be lost if the process stops. Transient failures are retried; a blocked front batch pauses later batches and makes readiness fail. Permanent rejections are recorded and later batches continue. The server attempts to drain queued reports during graceful shutdown; allow time and network access for this to complete.

## 9. Check delivery status

```bash
curl -i http://localhost:8000/status
```

`GET /status` returns a sanitized, read-only snapshot for the instance that answered, including when readiness is failing. It reports license and readiness state, Insights delivery counts and undelivered batches, and cached configuration snapshots. Counters and diagnostics reset when the process restarts; in a multi-instance deployment, each response describes one instance. Keep this endpoint on an internal operations network.
