## AsyncAPI Mock Configuration

AsyncAPI mocks use `runOptions.asyncapi` in `specmatic.yaml`. This is where Specmatic reads the async mock settings represented by `AsyncMockConfig`.

Start with [AsyncAPI Configuration](/supported_protocols/asyncapi/configuration) for the server model, inline and referenced servers, shared and per-spec settings, and complete examples.

<V3SpecmaticJsonYamlTabs
  v3Object={yaml.load(require('./includes/mock-configuration/v3/asyncapi/specmatic.yaml?raw'))}
/>

### AsyncAPI Mock Options

| Property | Description |
|----------|-------------|
| `type` | Must be `mock` for AsyncAPI service virtualization. |
| `servers` | Shared runtime server list. At least one effective server is required. |
| `servers[].server.host` | Broker host or endpoint for an inline server. |
| `servers[].server.protocol` | Messaging protocol used by the server. |
| `specs[].spec.servers[].server.$serverRef` | AsyncAPI 3 local server reference used in a per-spec override instead of `host` and `protocol`. |
| `servers[].server.type` | Required lifecycle: `external` or `in-memory`. |
| `servers[].server.adminCredentials` | Protocol-specific admin properties used to provision or inspect broker resources. |
| `servers[].server.client.producer` | Producer client properties passed through to the protocol client. |
| `servers[].server.client.consumer` | Consumer client properties passed through to the protocol client. |
| `specs` | Optional per-spec overrides selected by specification `id`. |
| `schemaRegistry` | Optional schema registry settings for Avro-based AsyncAPI mocks. |
| `schemaRegistry.kind` | Schema registry type. Currently `CONFLUENT` is supported. |
| `schemaRegistry.url` | Schema registry endpoint URL. |
| `schemaRegistry.username` | Optional username for the schema registry. |
| `schemaRegistry.password` | Optional password for the schema registry. |

### Notes

- Mark a server `type: in-memory` when Specmatic should start it. Kafka, JMS, and AMQP support in-memory brokers.
- Mark a server `type: external` when Specmatic should connect to an existing broker.
- `inMemoryBroker` is deprecated. Replace it with a server entry whose `type` is `in-memory`; see [migration guidance](/supported_protocols/asyncapi/configuration#migrate-from-inmemorybroker).
- `adminCredentials`, `client.producer`, and `client.consumer` are protocol-specific maps. For Kafka, use standard Kafka client properties.
- `schemaRegistry` is only needed when your AsyncAPI examples or payload schemas depend on a registry.
- For Kafka-specific guidance, see [Kafka](/supported_protocols/asyncapi/kafka).

## gRPC Mock Configuration <CommercialBadge/>

gRPC mocks use `runOptions.protobuf`.

```yaml
runOptions:
  protobuf:
    type: mock
    port: 50051
    importPaths:
      - ./proto-imports
    protocVersion: 3.25.5
```

`port` is optional when it is supplied by the command that starts the mock. `importPaths` supplies directories used to resolve imported proto files, and `protocVersion` selects the compiler version.

## GraphQL Mock Configuration <CommercialBadge/>

GraphQL SDL mocks use `runOptions.graphqlsdl`.

```yaml
runOptions:
  graphqlsdl:
    type: mock
    host: 0.0.0.0
    port: 9000
```

Both `host` and `port` are optional. When omitted, Specmatic uses the protocol defaults.

## Run Mock Server on Different Ports for Different Specifications

If you want to run mock server on different ports for different specifications, you can specify the port number in the `port` field under `consumes` key and assign the list of `specs` to it.

As per the above configuration, the specs `api_order_v1.yaml` and `api_uuid_v1.yaml` will run on port 9000 and the spec `online_store_v1.yaml` will run on port 9001.

You can also specify `host`, `basePath`, and even the complete `baseUrl` in the `consumes` field. For more details, refer to the [Service Virtualization](/contract_driven_development/service_virtualization#specmatic-configuration-with-base-url-host-port-and-path)

## Externalized Examples Directories

By default, Specmatic searches for the directory ending with `_examples` to pickup externalized examples. However, if needed, you can specify a list of directories containing externalized examples under `examples` key in specmatic configuration. Specmatic will retrieve the examples from these directories for use in both contract testing and service virtualization.

<V2V3SpecmaticConfigTabs
  v3Object={require('./includes/stub-configuration/v3/externalized-examples/specmatic.json')}
  v2Object={require('./includes/stub-configuration/v2/externalized-examples/specmatic.json')}
/>

:::note
When using v2 config, if the `_examples` directory is present, it will still be included alongside any additional
directories specified under the `examples` key.

When using v3 config, the examples will be loaded from directory with the name `${SPEC_FILE}_examples` if it exists,
in addition to any directories specified under the `examples` key. For example, if you have a spec file named
`api_order_v1.yaml`, Specmatic will look for examples in the `api_order_v1_examples`
directory by default, even if it's not explicitly mentioned in the configuration.
:::
