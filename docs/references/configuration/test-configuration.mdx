# Test Configuration

## Resiliency Tests

To enable [schema resiliency tests](/contract_driven_development/contract_testing#smart-resiliency-orchestration), add `schemaResiliencyTests` in a v3 configuration or `resiliencyTests` in a v2 configuration, as shown below:

<V2V3SpecmaticConfigTabs
  v3Object={require('./includes/test-configuration/v3/resiliency/specmatic.json')}
  v2Object={require('./includes/test-configuration/v2/resiliency/specmatic.json')}
/>

:::note
The resiliency test can be configured with the following options:
- `all` — will run both positive and negative tests
- `positiveOnly` — will not run negative tests
- `none` - the default
:::

:::info
When using configuration version 3, it is possible to set the `schemaResiliencyTests` option under `dependencies`,
or `systemUnderTest` or within a specific service. This allows you to enable resiliency tests for specific dependencies
or the system under test, while keeping it disabled for other services.
:::

## OpenAPI Test Run Options

Configure OpenAPI tests under `runOptions.openapi`. The options can be defined directly on a service or in `components.runOptions` and referenced by the service.

```yaml
runOptions:
  openapi:
    type: test
    baseUrl: http://localhost:8080
    filter: "PATH!='/health,/swagger'"
    swaggerUrl: http://localhost:8080/openapi.yaml
    actuatorUrl: http://localhost:8080/actuator/mappings
```

| Property | Description |
|----------|-------------|
| `type` | Must be `test`. |
| `baseUrl` | Base URL of the application under test. Alternatively, use `host` and `port`. |
| `filter` | Expression used to select the operations to test. |
| `swaggerUrl` | URL from which Specmatic can obtain the application's OpenAPI document. This can also be set for an individual entry in `specs`. |
| `actuatorUrl` | Spring Boot actuator mappings endpoint used for application API discovery. This can also be set for an individual entry in `specs`. |
| `workflow` | Workflow rules that extract values from one response and use them in later requests. |

swaggerUrl and actuatorUrl are mutually exclusive. You only need one of them.

When a run option contains multiple specifications, use the object form to override discovery settings for one specification:

```yaml
specs:
  - spec:
      id: orders
      swaggerUrl: http://localhost:8080/orders/openapi.yaml
```

### Security scheme credentials

Use `securitySchemes` on an OpenAPI specification entry to supply credentials by the security-scheme name declared in the OpenAPI document.

```yaml
specs:
  - spec:
      id: orders
      path: openapi/orders.yaml
      securitySchemes:
        oidc:
          type: openIdConnect
          token: "{OIDC_TOKEN}"
```

Supported `type` values are `oauth2`, `openIdConnect`, `basicAuth`, `bearer`, and `apiKey`.

### AsyncAPI Test Options

| Property | Description |
|----------|-------------|
| `type` | Must be `test` for AsyncAPI contract tests. |
| `replyTimeout` | Maximum time in milliseconds to wait for a reply message. Default: `10000`. |
| `subscriberReadinessWaitTime` | Additional wait time in milliseconds before tests begin verifying messages. Use this when consumers or subscriptions need time to become ready. Default: `0`. |
| `servers` | List of broker endpoints Specmatic can use while running the test. Specmatic matches entries by `protocol`. |
| `servers[].host` | Broker host or endpoint. For Kafka, this is typically `host:port`. |
| `servers[].protocol` | Messaging protocol such as `kafka`, `sqs`, `sns`, `jms`, or `rabbitmq`. |
| `servers[].adminCredentials` | Protocol-specific admin properties used to provision or inspect broker resources. |
| `servers[].client.producer` | Producer client properties passed through to the protocol client. |
| `servers[].client.consumer` | Consumer client properties passed through to the protocol client. |
| `schemaRegistry` | Optional schema registry settings for Avro-based AsyncAPI contracts. |
| `schemaRegistry.kind` | Schema registry type. Currently `CONFLUENT` is supported. |
| `schemaRegistry.url` | Schema registry endpoint URL. |
| `schemaRegistry.username` | Optional username for the schema registry. |
| `schemaRegistry.password` | Optional password for the schema registry. |

### Notes

- Add `replyTimeout` and `subscriberReadinessWaitTime` only when the defaults are not enough for your environment.
- `adminCredentials`, `client.producer`, and `client.consumer` are protocol-specific maps. For Kafka, use standard Kafka client properties such as `security.protocol`, `sasl.mechanism`, and serializer or auth settings.
- `schemaRegistry` is only needed when your AsyncAPI payloads reference schemas from a registry, such as the Kafka Avro sample.
- For Kafka-specific examples, see [Kafka](/supported_protocols/asyncapi/kafka).

## gRPC Test Configuration <CommercialBadge/>

gRPC contract tests use `runOptions.protobuf`.

```yaml
runOptions:
  protobuf:
    type: test
    host: localhost
    port: 50051
    importPaths:
      - ./proto-imports
    protocVersion: 3.25.5
    requestTimeout: 5000
```

`host` and `port` identify the server under test. `importPaths` supplies directories used to resolve imported proto files, `protocVersion` selects the compiler version, and `requestTimeout` is the request timeout in milliseconds (default: `5000`).

## GraphQL Test Configuration <CommercialBadge/>

GraphQL SDL contract tests use `runOptions.graphqlsdl`.

```yaml
runOptions:
  graphqlsdl:
    type: test
    host: localhost
    port: 8080
```

Both `host` and `port` are optional. When omitted, Specmatic uses the protocol defaults.

## Externalized Examples Directories

By default, Specmatic searches for the directory ending with `_examples` to pickup externalized examples. However, if needed, you can specify a list of directories containing externalized examples under `examples` key in specmatic configuration. Specmatic will retrieve the examples from these directories for use in both contract testing and service virtualization.

<V2V3SpecmaticConfigTabs
  v3Object={require('./includes/test-configuration/v3/externalized-examples/specmatic.json')}
  v2Object={require('./includes/test-configuration/v2/externalized-examples/specmatic.json')}
/>

:::note
When using v2 config, if the `_examples` directory is present, it will still be included alongside any additional
directories specified under the `examples` key.

When using v3 config, the examples will be loaded from directory with the name `${SPEC_FILE}_examples` if it exists,
in addition to any directories specified under the `examples` key. For example, if you have a spec file named
`api_order_v1.yaml`, Specmatic will look for examples in the `api_order_v1_examples`
directory by default, even if it's not explicitly mentioned in the configuration.
:::
